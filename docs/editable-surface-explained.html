Carbon's editable surface,
field by field

Carbon keeps its entire behavioural configuration in one versioned JSON file. This page covers the editable fields, the strategy values on their menus, and what each one does to the agent, as the surface stood in August 2026. It is a snapshot: tool_exposure — which tools the model is offered at all, as all, an allowlist, or query-match top-k — joined afterwards and is not described below. Part one

The surface

Carbon is a language model plus a harness. This page is about the harness's configuration.

The harness's behaviour used to be smeared across the code as module-level constants: the system prompt in agent.py, the truncation budget in limits.py, the summarizer prompt in compaction.py, constructor defaults buried in signatures. Changing behaviour meant editing code, and knowing which of five files to edit.

Now those knobs are a first-class primitive. One JSON file, harness/harness_config.json, is the entire editable surface. An editor that may touch only that file can retune the whole harness and nothing else, and the diff of what changed is the diff of one small file.

Three properties make it safe to hand over

  • Versioned. The file carries an integer version, bumped on every change. Rollback is reverting the file. Comparing two behaviours is diffing two versions of it.
  • Frozen. HarnessConfig is a frozen dataclass and every consumer binds its values at import. The lifecycle is edit, restart, revert to roll back. No in-place mutation, no hot reload.
  • Validated at load. load_config rejects unknown keys, missing fields, wrong types, non-positive counts, a strategy name not on its menu, and a malformed @path regex — loudly, at import. A malformed surface must fail the run, never silently fall back to a default the editor believed it had replaced.

Three zones

Not every field in the file is editable. Carbon publishes all three zones as data through surface_manifest(), and Refinery reads that rather than keeping its own copy — so a new field becomes proposable the day Carbon adds it.

Part three

The eleven editable fields

In the order they apply during a turn. Each card gives the current value, the bounds, the effect of moving it, and which tasks observe it.

Values are from config version 7. They change when a candidate is accepted, so treat them as a current reading rather than a fixed truth. uv run python -m loop.cli surface prints the live contract.

system_promptThe agent's default system prompt
Controls

The system message prepended to every conversation. It frames general disposition: explore before editing, prefer list_files and search_text over shell equivalents, read before changing, and never report done without running the project's tests.

Current (v7)

440 characters. The load-bearing clause is the last one: Never claim it works on your word alone — if you haven't run it, run it.

Bounds

Any string. The only field on the surface with no numeric bound and no menu.

Effect
Add framingReaches every provider call, so a single clause can shift behaviour across the whole suite at once.
Trim framingFrees window space and removes whatever that clause was holding up. The two are hard to separate.
CoverageEvery task that drives a live model — all of them except cluster H, which uses a scripted provider with no system message. That makes this the broadest field on the surface and the easiest to regress with. Trim the tool-use framing and D1 and D2 go red immediately; trim the verify-before-done clause and cluster B follows.
temperatureSampling temperature
Controls

The sampling temperature sent on every provider call.

Current (v7)

null — which is not the same as 0.0. Null means Carbon sends no temperature field at all and defers to the provider's own default. Every number, including 0.0, is a pin; null is the only way to match a harness that never pins the value.

Bounds

A number from 0 to 2, or null. JSON has one number type, so a proposed 1 is read as 1.0 rather than bounced on a type technicality.

Effect
LowerMore deterministic sampling. Less variance between attempts, and less chance of finding a second route through a hard task.
RaiseMore variance. On a suite that averages 3 or 5 attempts, this widens the spread on every pass fraction at once.
CoverageSame as the system prompt: every live-model task. Every provider call carries this value, so nothing that drives a real model is blind to it.
max_tokensDefault completion budget
Controls

The completion ceiling per provider call. A response that reaches it terminates with finish_reason=length, mid-sentence.

Current (v7)

4096

Bounds

Positive integer.

Effect
LowerLong generations truncate. The agent did not fail; it was not allowed to finish.
RaiseHeadroom for long output. Costs more, and a long reply consumes more window on the next turn.
CoverageG1 is the sole observer, and it binds hard: it needs roughly 1,878 completion tokens, about thirty times the next-hungriest task (B1's ~52-token tool-call arguments). No task fails because this is too small, so the field is guard-only — defended, not mined.
default_context_limitContext-window budget
Controls

The approximate token budget for the transcript. Not a hard wall — it is the base the compaction trigger is computed from.

Compaction fires when the estimated window exceeds limit × trigger_fraction. The estimate counts message content and tool-call arguments alike, at about four characters per token.

Current (v7)

4000 tokens, with compaction.trigger_fraction = 0.8, so compaction fires above 3200.

Bounds

Positive integer.

Effect
LowerCompaction fires sooner and more often. Every additional pass is another chance to lose a fact.
RaiseMore history carried verbatim. Costs more per call, and models attend to the head and tail of a long window far more reliably than the middle.
CoverageA1 and A3. A1's window peaks around 3,630 tokens against the 3,200 trigger, so compaction genuinely fires and this field moves it. A3 peaks around 1,185 and never compacts, so it observes the lowering direction only. G2 is not an observer — it pins context_limit=700 itself. Nothing fails on window size, so this field is guard-only.
compactionTranscript compaction policyStrategy menu · 3
Controls

When the trigger fires, compaction keeps keep_head messages at the front, keeps a tail, and replaces the middle with a single system-role checkpoint message. This object decides how all of that is done.

Current (v7)

strategy: token_budget_checkpoint keep_head: 2 keep_tail: 4 trigger_fraction: 0.8 summary_max_tokens: 1024

Parameters

keep_head, keep_tail, summary_max_tokens — positive integers. trigger_fraction — greater than 0 and at most 1.

Two structural rules apply whatever the strategy. Head and tail boundaries are snapped to whole-turn cuts, so compaction never orphans a tool result from its assistant tool_calls message — the API rejects that with a 400. And if snapping leaves nothing safe in the middle, the history is returned unchanged: a large window this turn beats a corrupt one.

Strategy menu
summarize_middle

Cut point by message count: keep the last keep_tail messages. The summarizer receives only the base compaction_prompt. Whatever comes back is used as-is.

Consequence: the checkpoint is free-form prose. A file list can come back as "some files", and nothing constrains that.
structured_checkpoint

Same cut point. The prompt is extended with nine required headings — goal, constraints, decisions, completed work, files read or changed, exact commands and tool calls, failures and rejected approaches, current state, next steps — plus instructions to merge any earlier checkpoint and preserve identifiers, paths, arguments and error tails verbatim.

Consequence: still prose, under headings. A heading can be satisfied with a vague sentence, and the prior checkpoint is folded into the transcript as ordinary history, so it is re-compressed on every pass.
token_budget_checkpointCurrent

Three substantive differences from the other two.

1 — the cut point is a token budget. Walk back from the newest message until recent_token_reserve tokens are retained, then snap back to the enclosing turn boundary. The newest message is always kept even if it alone exceeds the reserve, and the cut never crosses head_end.

2 — the prior checkpoint is passed as its own message, labelled as existing state to update, and removed from the material to be compressed. If the middle held only the prior checkpoint, it is carried forward verbatim rather than re-summarised.

3 — a deterministic state block is appended after summarizing. The set of paths read and paths modified is extracted from the assistant's actual tool-call arguments, merged with the previous block, and attached verbatim.

Why 1: a fixed message count is a proxy that fails in both directions. Four tail messages are nearly nothing after a turn of one-line acknowledgements, and far over budget after a turn that read a file. Why 2: a model shown the same content twice — once as "carry this forward" and once as "compress this" — compresses it. That double presentation is precisely how a fact erodes across repeated compactions. Why 3: the file list stops being something the summarizer must remember and becomes something the harness knows. Extracted from tool-call arguments rather than tool results, because a result can be an error string and a failed call still records what the agent was working on.
Additive parameters, valid only under this strategy
recent_token_reserve — default 0, disabled
Tokens of recent history to retain. At 0 there is no budget to enforce, so the strategy falls back to the plain message-count cut used by the other two. Also changes the compaction floor: under a budget, keep_tail is not the mechanism, so gating on it would refuse to compact a short-but-enormous history.
completion_reserve — default 0, disabled
Tokens held back for the reply. trigger_fraction scales with the window, but a completion does not: the reply that has to fit is about the same size at 4k and at 128k, so a fraction that leaves room at one leaves far too little or absurdly much at the other. Whichever trigger is tighter wins, so adding a reserve can only ever compact earlier.
checkpoint_fallback — default head_tail
Which positional truncation strategy bounds a checkpoint that outgrows summary_max_tokens × 4 characters. The deterministic state block is attached after that cut, so the state that must not be paraphrased also cannot be truncated away.
CoverageMiner: G4. Guards: A1 and G2. A3 never compacts, so nothing in this object can move it. H2 is not an observer either: it detects the summarizer call by payload shape rather than prompt text, which makes it invariant to every sub-field here by construction — and tests/test_registry.py asserts that invariance directly.
compaction_promptThe summarizer's base instructions
Controls

The system message for the summarizer call. Each strategy above appends its own extension to this text.

Current (v7)

It asks for a short checkpoint another model will use to continue, and enumerates what must be preserved verbatim: every concrete fact, code, name, decision, file path, and the current goal and next step. It closes with Be terse but lose nothing the next turn needs.

Bounds

Any string.

Effect
Demand moreNaming a class of state raises its retention odds. Naming everything produces a long checkpoint, which consumes the window compaction just freed.
Demand lessA shorter checkpoint, and more of the retention decision delegated to the summarizer.
CoverageThe same three as the object above. Miner: G4. Guards: A1, G2. H2's shape-based detection exists precisely so a legitimate rewrite of this field cannot make that fixture misread a summarizer call as a main call and report a recovery regression that never happened.
file_injectionTruncation policy for @path context blocksStrategy menu · 2Unguarded
Controls

When the user's message matches the @path pattern, the named file is read and injected as a context block. This object decides what survives if the file exceeds the budget.

It applies only on an @path match. No other route into the window uses it.

Current (v7)

strategy: head_tail budget: 4000 tail_fraction: 0.5

So an oversized file arrives as 2,000 leading characters, a truncation marker, and 2,000 trailing.

Parameters

budget — positive integer, in characters. tail_fraction — strictly between 0 and 1, the share of the budget spent on the suffix.

Under budget, the text passes through unmodified. Truncation is a no-op, not a reformat.

Strategy menu — see the comparison in part four
keep_head

Retain a prefix of budget characters, append a marker recording how many were dropped.

head_tailCurrent

Retain a prefix and a suffix, with the marker inserted between them.

CoverageMiner: A4. Guards: none. A4 is the suite's only @path sender and has no tools, so the injected block is its sole route to the answer — which also makes it the only observer, and it is already the miner. This field has something to mine and nothing to regress against. Closing that needs a second @path task with a passing prior, not a table edit.
tool_outputTruncation policy for tool resultsStrategy menu · 3
Controls

Every tool result passes truncation exactly once before entering the transcript. When the result exceeds the budget, this object decides what happens to it.

This is the most consequential field on the surface. A command emitting 840,000 characters cannot enter a few-thousand-token window, so something has to give.

Current (v7)

strategy: head_tail budget: 4000 tail_fraction: 0.6

So an oversized result arrives as 1,600 leading characters, a marker, and 2,400 trailing.

Trust domains

Tool output is untrusted, so it is handled by truncate_tool_result rather than truncate. Any line resembling one of the harness's own recovery footers is relabelled as quoted text before the cut — before, so an attacker cannot inflate the excerpt past the budget by packing it with lookalikes.

That relabelling applies to the model's copy only, never to anything written to disk or re-applied. A relabelled git diff, spilled to a file and re-applied, wrote five corrupted lines and reported success: an add-only hunk has no context line for the patcher to mismatch.

Strategy menu
keep_head

Retain a prefix. Appropriate when the salient content is at the start — a header, a summary line.

Consequence: a test suite that prints thousands of PASS lines and then one FAILED line loses the failure entirely.
head_tailCurrent

Retain a prefix and a suffix. Appropriate for command output, where the actionable line is usually last.

Consequence: the middle is unrecoverable. There is no route back to it.
offload_to_file

Lose nothing. The complete result is written to .carbon/offload/<sha256-prefix>.txt under the workspace root. The model receives the same head-and-tail excerpt plus a footer naming the file — as a workspace-relative path, so the model's own read_file resolves it — and giving the exact next call: a ranged read, or a search_text with the pattern spelled out.

What changes: the middle is withheld rather than destroyed. It is one tool call away. Scope and small print. Offered on the tool-result menu only; file_injection does not get it, because an @path block is already re-openable and copying it would hand the model a duplicate of what it holds. It is best-effort by construction: it runs mid-turn after the assistant's tool_calls are already in the transcript, so a failed write degrades to a plain head_tail excerpt and says so in the marker rather than abandoning the turn. The filename is a content hash, so a repeated identical result re-lands on the same file. The write is atomic via a private temp file and a replace, which matters because the name is deterministic and a workspace the agent does not own could pre-place a symlink there. Only the newest 64 spills are retained, and the directory is git-ignored. One interaction worth knowing: when the caller supplies a continuation hint — as read_file does — the strategy downgrades to head_tail for that call, so the model is offered one recovery route rather than two. Otherwise a paged read would spill a copy of a file it is already holding, one file deeper every time.
CoverageMiners: E1, E3, E4. Guards: E2, D3.

The nuance is worth stating precisely. E4 is the task an offload configuration can genuinely turn green: it gates the pass on recovery from the offloaded artifact itself, so neither a larger budget nor a luckier excerpt can fake it. E3 stays red even under offload, because its verifier requires the value inside the first plain run's inline result; the only values that satisfy that are flood-sized budgets, which E1's economy verdict prices out. E2 and D3 catch the opposite failure — a candidate that floods the window or loses the tail dies on them.

Two deliberate exclusions from this field's observer set. A2 is not listed: its value survives every budget down to 8,736, so no legal value moves its verdict either way. C1 and C2 are not listed either, and that is now a property of the code — their leak predicates read the raw tool result, precisely so a candidate cannot raise a containment score by clamping away the evidence.
max_tool_stepsTool-call rounds per turn
Controls

The hard cap on tool-call rounds within a single turn before the agent loop gives up. It is the loop's only stop condition by default; there is no wall-clock bound unless a caller opts into one.

Current (v7)

20

Bounds

Positive integer.

Effect
LowerDeep tasks terminate half-finished. The agent is not confused; it exhausted its rounds.
RaiseDeeper chains complete. A stuck loop also runs longer before giving up, and every round is a provider call.
CoverageObserved by every task that makes a tool call. F2 is the binding guard: it forces ten provider calls and fails at any budget of 9 or less. F1 and G3 also observe, but need roughly 3 and 2 rounds, so F2 dominates them. Nine observers have failure headroom, yet none fails on depth, so raising the budget cannot turn any of them green — the field is guard-only.
retryTransient provider-failure policyStrategy menu · 2
Controls

What happens when a provider call raises for a reason unrelated to the work — rate limiting, a 503, a brief outage. Whether to retry, how many times, and the delay schedule.

Current (v7)

strategy: backoff max_attempts: 5 base_delay_ms: 2000

Parameters

max_attempts — integer from 1 to 5. It bounds total tries, not retries: at 3, a delay is offered after try 1 and try 2 and refused at try 3, for three tries in all.

base_delay_ms — integer from 0 to 10,000. Delay before try n is base_delay_ms × 2^(n−1) milliseconds.

Strategy menu
fail_fast

No retry. One call, and the exception propagates.

Note: can_retry is gated on the strategy, so this ignores max_attempts entirely. Under fail_fast the call count is exactly 1 whatever the number says — which is why H3 derives its expectation from both fields, not from max_attempts alone.
backoffCurrent

Retry with exponential backoff. At the current values the delays are 2s, 4s, 8s and 16s, for five tries in total.

Consequence: a genuinely dead provider keeps the turn alive for about 30 seconds before the exception surfaces.
CoverageH1 is the only observer: it fails under fail_fast at any attempt count, and under backoff with max_attempts=1. H2 takes the overflow branch, which returns before can_retry is consulted. H3 derives its expectation from the same config Carbon reads, so it passes for all ten legal pairs — invariant by construction, which makes it a canary for Carbon's retry code rather than an observer of this field. base_delay_ms is observed by nothing at all; it only feeds a sleep. Guard-only.
verify_attemptsRe-prompts before a turn is marked unverified
Controls

When a turn changes code and the instruction root declares a test command under ## Testing, the agent may not report done until a real passing run of that command is observed after the change. The model runs it with bash; the harness only watches the receipts. This field caps the re-prompts.

On exhaustion the reply is marked unverified. The gate never implies a pass it did not observe.

Current (v7)

3

Bounds

Positive integer. Note that whether the gate exists at all is a locked field, require_run — Refinery may tune the re-prompt count, never the gate.

Effect
LowerFewer chances for the agent to go back and run the tests, so more turns end marked unverified.
RaiseMore chances to comply, and more wasted provider calls when the agent was never going to run them.

Part five

What is locked, and why

The boundary is what makes the surface trustworthy. Without it, "editable" would mean "anything".

Seven non-editable fields

These live in the same file as the eleven. Carbon marks them non-editable in its schema, and Refinery reads that marking rather than maintaining its own list.

FieldReason
require_runWhether a code change must be backed by an observed passing test run. Making the verification gate optional would make honesty optional. Part of verification integrity.
approval_toolsWhich tools the approval gate guards. Part of the permission system, not an optimisation surface.
code_extensionsWhich file extensions arm the test gate on write or edit. Shortening the list would silently disarm the gate for whole languages.
attach_patternThe regex recognising an @path reference. A context-delivery parser contract, not an optimisation knob. Must compile and carry at least one capture group; the use site extracts via group(1).
memory_search_limitMax hits from cross-session recall. Locked until the suite has miners and guards that can observe it. An unobserved field is not a safe field to tune.
max_item_charsA compatibility re-export only. The real budgets live in file_injection.budget and tool_output.budget through their policy objects.
versionManaged by the pipeline. Incremented automatically on every accepted edit.

Six immutable invariants

These are correctness and trust properties, not optimisation choices. They are not in the file at all. Carbon publishes them beside the editable schema so an external improver does not waste proposals on behaviour it is intentionally forbidden to weaken.

InvariantWhat it guarantees
tool_argument_validationMalformed or incomplete tool calls never execute.
unique_atomic_editsAn edit must match exactly once and report the resulting diff.
workspace_and_secret_boundariesNo strategy may expand file access or weaken secret-file refusal.
subagent_workspace_identityDelegated workers use the workspace explicitly bound by the parent, read-only. A worker runs under its own Policy, so a mutating tool would execute outside the parent's approval gate.
verification_integrityFresh, real test receipts and fail-closed verification are not editable.
strategy_registry_and_config_validationRefinery may select vetted strategies. It may not install executable code hooks.
Why the last invariant is the load-bearing one

Refinery selects from menus that Carbon authored and reviewed. So when Refinery finds an improvement no menu value can express, it cannot invent one. It has to write the request down and hand it to a person.

There are exactly three candidate kinds. A configuration_candidate can be applied and evaluated automatically. A strategy_surface_gap needs a reviewed Carbon strategy implementation first. A correctness_defect needs a locked Carbon fix, and must never become a knob.

offload_to_file started as the second kind. E3 held that slot from the suite repair onward, recorded as "needs a tool_output strategy that preserves the middle of a large result — an offload that hands back a retrievable path". A person read that request and implemented the strategy. The gap entry left the table when the strategy shipped, not when the task was softened.

Part six

Which fields are observed

A field is only safe to tune if some task can report that you made things worse.

Refinery's coverage table assigns each field three roles, and the ordering between them is what the tests enforce.

  • Observers — tasks whose mechanism genuinely routes through this field and whose verdict some legal value can move. "Reads a tool result" is not enough: a 45-character result never meets a 4,000-character budget, so the task is invariant and the coverage is decorative.
  • Miners ⊆ observers — observers with failure headroom that moving the field could turn green.
  • Guards ⊆ observers — observers that can still regress, meaning their prior is not already fail. A task already at 0.0 cannot drop further.

Guard-only is not a defect. It means every observer already passes, so there is nothing to mine and only something to protect. Four fields sit there. Note the precise claim for max_tool_steps: it has nine observers with failure headroom, but none of them fails on tool-round depth, so raising the budget cannot turn any of them green. "No failing observer" would be plainly false.

Unguarded is a real gap, recorded rather than hidden behind a guard that cannot see the field. file_injection's only observer is A4, which is also its miner, so a candidate can be measured as an improvement with nothing able to catch a matching regression. Closing it needs a second @path task with a passing prior.

One more absence worth naming explicitly: base_delay_ms is observed by nobody. It only feeds time.sleep, and no verifier measures elapsed time.

The table also carries no capability gaps today. That slot was held by E3 — "needs a strategy that preserves the middle of a large result" — until Carbon shipped offload_to_file, at which point E3 moved to that field's miners with E4 alongside it to prove path-recoverability specifically.

What no test can enforce, stated plainly

The observer tuples are authored assertions about Carbon's internals. An audit found six of them false at once, and padding a row with irrelevant task names satisfies every mechanical check — the subset rules only relate the roles to each other, never to Carbon. A reviewer has demonstrated a plausible new field passing the whole contract with no real coverage.

So this is a human-audited claim with mechanical guardrails, not a proof. Changing a row means re-measuring, not editing a tuple. The table also lives in loop/ rather than runner/ on purpose: runner_sha is a content hash of the runner package and every recorded result is stamped with it, so correcting a row here does not invalidate every baseline.
